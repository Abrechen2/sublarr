  • Breadcrumbs show the selected item's name as the current leaf. Save-state pill top-right.

Template B pattern:
  • Scrollable form with repeated SettingsSection blocks — one concept per section, description below title.
  • Right sticky TOC with anchor jumps + section count badge. Cap at 5-6 sections. At 7+ split into a sub-page.
  • Expert-mode indicator in TOC panel — shows how many items are currently hidden behind the toggle.
  • No master list on the left — this is a bounded, finite set of settings that belong together.

Template C pattern (the one Codex insisted on — separate from A and B because the primary UX is "understand what wins" not "edit this object" or "fill this page"):
  • Left: scope tree (Global → Profile → Series/Movie). Overrides badged in amber. Current selection highlighted in cyan.
  • Right top: Resolved headline — one setting with its full resolution chain displayed left-to-right. Overridden steps are struck through; the winner is highlighted.
  • Right center: Override widget — three-state (Inherit / Force X / Force Y). Inherit keeps in sync with the parent scope; Force pins.
  • Right bottom: Summary list of all other rules at this scope with inherited vs overridden pills. No raw form fields — everything is presented as a decision.
  • No tree-view as a separate page template — the tree is a control inside the left pane here, not its own archetype. (Codex's explicit instruction.)

Adopting the scaffolds — Hybrid Ratchet (Codex recommendation)

Step 1 — Land the primitives

  • Extract <CollectionLayout> + <FormLayout> + <RulesLayout> as pure layout components
  • Shared primitives: <InheritanceRow> · <BudgetBar> · <ApiKeyField> · <HealthRail>
  • No page rewrites yet. Scaffold exists but unused.

Step 2 — Three reference migrations

  • General → FormLayout (reference for B)
  • Providers → CollectionLayout (reference for A)
  • Profiles & Overrides → RulesLayout (reference for C)
  • These three become the canonical examples every other page converges toward.

Step 3 — Ratchet everything else

  • Any new Settings page: must use a template. No exceptions.
  • Any existing page touched for feature work: migrate it as part of that work.
  • Pages never touched for features: stay legacy — no speculative rewrites.
  • Convergence without stalling the product. Solo-maintainer-safe.
Rule: never combine a framework-migration commit with a feature commit. Migrate first, ship behind the template, then add new features on top. This keeps bisect-ability and PR reviews sane.
